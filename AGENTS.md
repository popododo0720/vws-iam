# AGENTS.md

Rules for anyone changing this repository, human or agent. A rule with an enforcer fails a check when it is broken. A rule marked judgment has no check, so the author and the reviewer carry it. Design: #1.

## Layout

| Package | Owns |
| --- | --- |
| `internal/iam` | Domain types (users, groups, roles, managed policies, access keys, MFA devices, FIDO security keys, instance profiles, SAML providers, OpenID Connect providers, account aliases, the account password policy, the root console login), validation, and ARNs. Pure. |
| `internal/store` | The `Backend` interface, typed helpers, and `Mutate` (read, apply, compare-and-swap, retry). `UpdateIf`/`DeleteIf` are conditional writes: they commit only while another object (`Pre`) is still at the version read, atomically with the write. `storetest` is the suite every backend passes. `Mutate` backs off with jitter between conflict retries. |
| `internal/store/memstore`, `internal/store/kubestore`, `internal/store/etcdstore` | The backends. `etcdstore` keeps each object in one etcd key under a prefix (`<prefix>/<kind>/<folded key>`, version = `mod_revision`); a conditional write is one etcd `Txn` comparing both objects' `mod_revision`, so it needs no fence. Every etcd call runs under a 5 s timeout; reads are tried 3 times on a transient failure, writes once (the client resends only an unsent request, at most 3 times). `kubestore` keeps each object in one `iam.vws.popododo0720.io/v1alpha1` custom resource in the service namespace. Kubernetes has no multi-object transaction, so a `kubestore` conditional write is serialized through resourceVersions (`fence.go`): it fences the precondition object by a compare-and-swap at the version read, and every `Update`/`Delete` of a fenced object first moves each fenced object off the version its pending write needs. |
| `internal/secret` | AES-256-GCM sealing under a KEK keyring loaded from systemd credential files (`LoadPrefixed`), a directory (`LoadDir`) or the environment (`FromEnv`). The KEK id is stored with each value; associated data binds a value to its owner. |
| `internal/password` | argon2id PHC hashes. |
| `internal/accesskey` | Access keys: create (secret returned once), list, status, delete, at most 2 per user, `GetSigningCredential`. |
| `internal/policy` | Policy parse/validate (`MalformedPolicyDocument`) and evaluation: explicit Deny > Allow > implicit deny, session policies narrow. Pure. |
| `internal/authz` | `Authorize`: gathers user, group, and role policies from the store and evaluates them. |
| `internal/sts` | `AssumeRole` (session policies: `Policy`, `PolicyArns`, #22), `GetSessionToken`, `DecodeAuthorizationMessage` (`authmsg.go`, #109), `GetAccessKeyInfo` (`keyinfo.go`, #108; session key ids through an expiring key index entry, #188), `GetFederationToken` (`federation.go`, #107), and `AssumeRoleWithSAML` (`saml.go`, `samlxml.go`, #106; test IdP in `samltest`; stored providers through `WithStoredSAML`, `samlstore.go`, #196). `OIDCKeyFetcher` (`oidckeys.go`, #208) reads an OpenID Connect provider's JWKS over TLS, pinned by its thumbprints. `sessionref.go` (#20) seals a session reference (identity and revocation generation, no secret) that `CheckSessionRef` re-checks as `Validate` does. The session token is the sealed session (KEK, AES-256-GCM), bound to its `ASIA` key id and its principal's unique id; `Validate` rejects tampered, mismatched, expired, and revoked tokens. `Resolve` derives the `Caller` (MFA, temporary) server-side; `RevokeSessions` bumps a revocation generation on the user or role (and records its time); a token carries the generation it read at issue, so revocation needs no replica clock (#46). |
| `internal/totp` | RFC 6238 TOTP (SHA-1, 6 digits, 30 s). Pure. |
| `internal/mfa` | Virtual MFA devices: create (seed shown once, stored sealed), enable with two consecutive codes within ±1 step, resync (two consecutive codes within ±20 steps; the stored drift shifts later checks), deactivate, delete, list, `Verify` with ±1 step around the drift and a replay guard; 5 wrong codes in a row lock the device for 15 minutes, doubling for each further lockout before an accepted code up to 1 hour (stored, survives restart, #29). FIDO security keys (`fido.go`): register an already verified WebAuthn credential, get by serial (AWS GetMFADevice), list, deactivate (delete). |
| `cmd/vws-iam` | Wiring and flags (`-listen`, `-store`, `-etcd-endpoints`, `-etcd-prefix` in `etcd.go`, the mutual TLS files `-tls-cert-file`, `-tls-key-file`, `-tls-client-ca-file` in `tls.go`, `-insecure-plaintext`, the AssumeRoleWithSAML service provider `-saml-audience`, `-saml-sign-in-url` in `saml.go`). `-store=etcd` (default) connects to `https://` endpoints with the client TLS files `etcd-ca.pem`, `etcd-client.pem`, `etcd-client-key.pem` from `$CREDENTIALS_DIRECTORY` (systemd `LoadCredential=`); `-store=memory` keeps state in one process. The store is checked with backoff before serving (#110). |
| `deploy/crds`, `deploy/rbac` | The CRDs and the namespaced store `Role`. vws-iam owns the IAM CRD schemas; vws-deploy only syncs them into its chart. |
| `internal/grpcapi` | vws.iam.v1 gRPC server: done-LRO mutations with request_id replay, AWS error codes in ErrorInfo `aws_code`, Authenticate (SigV4 canonical request, secret stays here), Authorize recheck; AssumeRole/GetSessionToken take the caller only from the request's `authentication` oneof (vws-proto v0.3.0): a SigV4 request re-verified here and resolved by `sts.Resolve`, or a console session token (`console_session_token` is root-only for GetSessionToken). Missing is UNAUTHENTICATED. UserService/RoleService `Revoke*Sessions` set `SessionsRevokedBefore` through `sts.RevokeSessions` (`revoke.go`) and report it as `sessions_revoke_time`. MfaDevice status carries `failed_attempts` and, only while locked, `locked_until` (vws-proto v0.4.0). A used STS SigV4 request is an `IamReplayEntry` in the shared store (keyed HMAC-SHA256 of key id and signature under a key derived from each KEK, expiry), so every replica refuses it; `GCReplayEntries` removes expired ones (run every 5 minutes by `cmd/vws-iam`, with `GCSessionKeys` for expired STS session key index entries, #188). Replica clocks must stay within `sigv4.MaxSkew` of each other: entries live 2×MaxSkew, and that margin is what covers cross-replica skew. A retry after a lost create response is refused once as a replay. Failed Login, MFA and STS-MFA attempts are also counted per user, access key and source IP in `IamAttemptCounter`s shared by every replica (`limit.go`); a caller over its limit is refused with Throttling (STS too: `sts.ErrThrottling` passes through `verifyMFA`), and a STS-MFA attempt throttled by the user's own limit renews a running device lock, capped at `mfa.MaxLockout` and never starting one (`mfa.RenewLock`, #44/#48), as does a console Login throttled by the user's limit (`lockrenew.go`); an IP- or key-only throttle does not. GC lists in pages (`store.Pager`). |
| `internal/sigv4` | Pure SigV4 verification. |
| `cmd/vws-iam` | `vws-iam` serves; `vws-iam bootstrap` (etcd store only) is the idempotent one-shot run importing the root key and, when given (`VWS_IAM_ROOT_PASSWORD` or a `password` file in `-root-credentials-dir`), the root console password. With `-store=etcd` the KEK is the credentials `kek_active` (active id) and `kek_<id>` (`secret.LoadPrefixed`); with `-store=memory` it is `VWS_IAM_KEK`/`VWS_IAM_KEK_ID`, `-kek-dir`, or random. |

## English only

Write everything in this repo in English: README, code comments, docs, AGENTS.md, QUALITY.md, PR and issue templates, commit messages, PR and issue bodies, review comments and `Verified-by` sections. The `english` job in CI runs `scripts/check-english.sh`: `files` fails on a tracked file with Hangul unless `.github/english-allowlist` lists it as `<glob> <reason>` (only test data and user-facing UI strings belong there), and `text` and `commits` reject Hangul in the PR body and the PR's commit messages with no exception.

## /correct loop

1. When a bot is corrected (by the user Su Kim, tmp or eggbot, or by a failed `vws verify`), it opens an issue the same day with the `incident` label using the `.github/ISSUE_TEMPLATE/incident.yml` form. It must fill in the correction and "the check that would have caught this".
2. Every few days vws-verify runs a gardener pass. It groups open incidents by cause and promotes repeated ones to a check (test, lint, guard rule, archtest), not a sentence. The check must actually fail on an input that contains the mistake.
3. When the promoting PR is merged, close the incident with its link. An incident that will not be promoted is closed with the reason.
4. The milestone report (to tmp) lists the number of incidents in the period and the checks promoted.
5. The `incident` label is defined in `.github/labels.yml`, copied from vws-deploy. That file is only a definition and does not create the label on GitHub. `scripts/guard.sh correct` runs `scripts/guard-agents.sh correct`, which checks this section and its body, the required fields of the form and the label definition; the `ci` workflow's `lint` job runs it on every pull request and `scripts/guard_test.sh` shows it fails on an empty section.

## Insider-risk guardrails

Bots are insider risks too. These rules have no exceptions. Design: `popododo0720/vws-deploy#33`.

1. **Independent verification.** The bot or model that wrote a change does not verify it. Another bot or a person does. This is process, and CI cannot enforce it.
2. **Record.** Every change is an issue, then a PR with `Part of #N`, then commits. The PR body says what changed, how it was verified, and what was not verified. No force-push or history rewrite without the user's approval.
3. **Failing tests.** A new feature is not tested on the happy path alone. It has at least one case each for power loss or restart, idempotent replay, and hostile or boundary input. Otherwise the PR says why one is impossible.
4. **Least privilege.** No push to `main`. Every change is one PR from its own branch off `main`. No stacked PRs and no local merges. Tokens are scoped to this repository. RBAC covers only what the code calls, in a namespaced Role where possible (`vws-deploy` `docs/rbac.md`).
5. **Separate audit.** The author, the verifier, and the merge decision are different. The author never merges its own PR. Merge only when the base is `main` and every check on the head commit is success.
6. **Isolation and stop.** To stop a bot, end its session and revoke its token. Risky work runs only in the box or a throwaway cluster. No access to a production cluster.
7. **Incident disclosure.** A broken rule or an incident is written up in an issue labeled `incident` with cause, impact, fix, and prevention.

Repository items:

- Reboot recovery. All state is in the backend; a restart rereads it (`storetest` `ReopenKeepsState`).
- Idempotent replay. A second create of the same name is `ErrExists`, a stale write is `ErrConflict` (`storetest`).
- Hostile input. Invalid names, paths, unsealed secrets, and non-argon2id hashes are rejected before any write (`TestValidateRejectsHostileInput`, `InvalidObjectIsNotStored`).
- RBAC. `deploy/rbac/role.yaml` lists only the verbs `kubestore` calls.
- No AWS account ID digits anywhere in the repository.
- Checks: `.github/workflows/repo-guard.yml` runs `scripts/guard-agents.sh` on every pull request (base is `main`, body has `Part of #N` and no closing keyword, this section has items 1 to 7). It is a caller of the vws-deploy `repo-guard-<job>.yml` workflows, every `uses:` pinned to one 40-hex vws-deploy main SHA (vws-deploy `docs/design/repo-guard-reusable.md`); a pin bump changes only those SHAs. `.github/workflows/direct-push-watch.yml` reports a commit that reached `main` without a pull request. Detection, not a block. That file and the script are copied as-is from `vws-deploy`. The Judgment count lives in `TestAgentsRulesNameAnEnforcer`, not in the shared script.

### Script push, PR and merge

A deterministic script (the factory orchestrator in vws-deploy `docs/factory-orchestrator.md`, the handoff submit) may push a branch, open a pull request and merge one. A script merge happens only when all of these hold:

- every CI check on the head commit is green;
- `verify-gate` passes;
- the `vws-verify` App check run passes;
- the pull request has no conflicts;
- the merge is a squash, made with `--match-head-commit` set to the verified head;
- the pull request is not labeled `blocked`.

`ORCHESTRATE_MERGE=apply` is approved only under these conditions. The lead (dr eggbot) is woken only for a decision or a failure (issue scope, real conflicts, a failed check), not for a routine push, pull request or merge. Guardrails 1, 4 and 2 still hold: the author bot is never the verifier, nothing pushes to main, and every pull request body has `Part of #N` with no closing keyword.
